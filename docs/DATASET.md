# 数据构建说明

## 构建顺序

1. 在 `scripts/build_data.py` 的 `MODULES` 中编写模块事实：入口、角色、必填字段、状态、额度、保留期、常见错误、排查步骤和通知触发条件。
2. 每模块生成12个有不同业务用途的章节，加上16个专项规则，形成16份Markdown手册及208个检索片段。
3. 每个片段生成8种问法，得到1,664条FAQ。它们是模板表达，不是人工标注的自然用户提问。
4. 使用固定种子20260925采样FAQ，加入虚构组织标识、渠道和会话编号，输出6,000条模拟会话。没有姓名、电话、支付卡或真实用户身份。
5. 清单记录每个数据文件的字节数及SHA-256。`check_data.py`校验ID唯一、文档引用、数量、文本去重及FAQ/工单来源关系。

所有时间限制、额度和产品行为都是演示规则，不是厂商政策或性能测试结果。相同模板跨模块生成的记录具有相关性；单纯增加模块组合或会话采样不会带来等量的新知识。

## 文件约定

- `manuals/*.md`：来源文档，可按业务模块阅读；每个二级标题包含知识ID。
- `knowledge.jsonl`：实际进入检索的资料；`parent_id`指向手册，`source`指向具体文件。
- `faq.jsonl`：每条含问题、答案和`source_id`；不直接用作独立评测集。
- `simulated_tickets.jsonl`：每条含虚构组织、渠道、两轮对话、`source_id`与合成标志。
- GitHub随仓库提供上述两张表的完整 `.gz` 压缩文件；生成器在本地产生明文和压缩版。清单校验针对解压后的逻辑内容，避免把压缩包装重复计为新资料。
- `manifest.json`：构建版本、种子、数量、文件哈希；不含用户上传资料。
- `evaluation/cases.json`：另外编写的44道开发回归题，绝不加载进索引。开发中用过这些题诊断失败，故不称盲测集。

## 如何扩成真实业务知识库

优先收集实际产品手册、SOP、经批准的退费政策、真实匿名化工单和产品版本说明；逐条保留文档负责人、生效日期、适用套餐、来源和失效日期。统一冲突政策后再切分、索引。按业务意图或文档分组拆分评测，避免同一FAQ的改写同时出现在知识库和测试题里。

对外报告应区分文档数、唯一事实数、片段数、问法数和会话数。声称80万检索片段时，需要相应去重语料、资源记录、索引规模和性能结果。当前可选80万模拟工单只用于生成与导入实验，不等同于80万知识事实或系统已支持80万检索。

## 再生成

`python scripts/build_data.py`会按固定规则重建种子派生文件，不删除用户上传目录。`--tickets N`只改变模拟会话条数。更改种子数据后重启服务；更改本地上传资料可重新导入。默认语料确定性可复现，环境相关运行时延不保证相同。
